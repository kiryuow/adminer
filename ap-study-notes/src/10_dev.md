## 1. 開発プロセスとモデル

### 共通フレーム（SLCP）

**共通フレーム** とは、ソフトウェアの企画から開発・運用・廃棄までの作業内容や用語を標準化した枠組みです。発注者と受注者が「要件定義」などの言葉の意味を共通に理解できるようにするのが目的です（日本では「共通フレーム2013」）。

### 開発モデル

| モデル | 特徴 |
|---|---|
| **ウォーターフォールモデル** | 工程を上流から下流へ順に進め、原則として前の工程に戻らない。計画や進捗管理がしやすいが、仕様変更に弱い |
| **プロトタイピングモデル** | 早い段階で試作品（プロトタイプ）を作り、利用者に確認してもらいながら要求を明確にする |
| **スパイラルモデル** | システムをいくつかの部分に分け、設計・開発・評価のサイクルを繰り返して徐々に完成させる |
| **アジャイル** | 短い期間の反復（イテレーション）で、動くソフトウェアを少しずつ開発する。変化への対応を重視 |

## 2. 要件定義

- **機能要件**：システムが何をするか（受注を登録できる、売上を集計できる）。
- **非機能要件**：性能、可用性、セキュリティ、使いやすさなど、機能以外の品質に関する要件（応答時間3秒以内、稼働率99.9％）。
- **要求の分析手法**：インタビュー、アンケート、業務の観察、**ユースケース**（利用者とシステムのやり取り）、**ユーザストーリー**（「〇〇として、△△したい、なぜなら□□だから」という形で要求を書く）。

## 3. 設計の手法

### 構造化分析と DFD

**DFD（データフロー図）** は、業務やシステムの中で **データがどこからどこへ流れ、どう処理されるか** を表す図です。処理の順序や条件は表しません。

| 記号 | 意味 |
|---|---|
| ○（円・バブル） | プロセス（処理） |
| → （矢印） | データフロー（データの流れ） |
| ＝（二重線） | データストア（ファイル・DB） |
| □（四角） | 外部実体（データの発生源・行き先：顧客など） |

### オブジェクト指向

**オブジェクト指向** は、データと、そのデータを操作する手続（メソッド）をひとまとめにした **オブジェクト** を単位としてシステムを組み立てる考え方です。

| 用語 | 意味 |
|---|---|
| **クラス** | オブジェクトの設計図（ひな形）。そこから作られた実体が **インスタンス** |
| **カプセル化** | データと手続をまとめ、内部の詳細を隠す。外部からはメソッド経由でしか操作させない（情報隠蔽） |
| **継承（インヘリタンス）** | 上位クラス（スーパクラス）の性質を、下位クラス（サブクラス）が引き継ぐ |
| **汎化と特化** | 共通部分をまとめて上位クラスを作ること（汎化）。その逆が特化。「is-a」の関係 |
| **集約と分解** | 全体と部分の関係（車とタイヤ）。「part-of」の関係 |
| **ポリモーフィズム（多相性）** | 同じメッセージを送っても、受け取ったオブジェクトによって異なる動作をする |
| **オーバーライド** | サブクラスで、スーパクラスのメソッドを再定義する |

### UML

**UML** は、オブジェクト指向の設計で使う図の表記法を統一したものです。

| 図 | 表すもの |
|---|---|
| **ユースケース図** | 利用者（アクター）とシステムの機能（ユースケース）の関係 |
| **クラス図** | クラスの属性・操作と、クラス間の関係（関連・汎化・集約）、多重度 |
| **シーケンス図** | オブジェクト間のメッセージのやり取りを **時間の順序** に沿って表す |
| **コミュニケーション図** | オブジェクト間のメッセージのやり取りを、**つながり（構造）** を中心に表す |
| **アクティビティ図** | 処理の流れ（フローチャートに近い）。並行処理も表せる |
| **ステートマシン図（状態遷移図）** | オブジェクトの状態と、イベントによる状態の変化 |

### モジュール設計 ― 強度と結合度

プログラムを機能ごとの部品（**モジュール**）に分けるとき、良い分け方の基準が **モジュール強度** と **モジュール結合度** です。

### デザインパターン・その他の設計技法

- **デザインパターン**：オブジェクト指向設計でよく使われる設計の型。Singleton（インスタンスを1つだけにする）、Observer（状態変化を複数に通知する）、Factory など。
- **MVC モデル**：アプリケーションを Model（データと処理）、View（表示）、Controller（入力の受付と制御）に分ける。
- **共通処理の部品化・再利用**：同じ処理を何度も書かず、ライブラリやフレームワークとして再利用する。

## 4. テスト

### テストの種類（V字モデルの右側）

| テスト | 内容 |
|---|---|
| **単体テスト** | モジュール（部品）単位で、プログラム設計どおり動くか確認する。**ホワイトボックステスト** が中心 |
| **結合テスト** | モジュールを組み合わせて、インタフェースが正しいか確認する |
| **システムテスト** | システム全体が要件（性能・セキュリティなどの非機能要件も含む）を満たすか確認する |
| **運用テスト（受入れテスト）** | 利用者が、実際の業務の環境で使えるか確認する |
| **回帰テスト（リグレッションテスト）** | 修正や変更によって、**それまで正常だった部分に悪影響が出ていないか** を確認する |

### テストの支援と品質の評価

- **スタブ**：上位モジュールから先にテストする（トップダウンテスト）とき、未完成の **下位** モジュールの代わりをする仮のモジュール。
- **ドライバ**：下位モジュールから先にテストする（ボトムアップテスト）とき、未完成の **上位** モジュールの代わりに呼び出す仮のモジュール。
- **バグ曲線（信頼度成長曲線）**：テスト時間と発見したバグの累積数のグラフ。S字型で、終盤に増加が鈍って **収束** していれば品質が安定してきたと判断できる。
- **エラー埋込み法**：わざと既知のエラーを埋め込んでテストし、その発見率から、残っている未知のエラー数を推定する。
- **カバレッジ（網羅率）**：テストで実行された命令や分岐の割合。

## 5. レビュー

テストは「作ったものを動かして」確認しますが、**レビュー** は設計書やソースコードを「人が読んで」誤りを早期に発見する活動です。上流工程の誤りほど、後で直すコストが大きいので、早期発見が重要です。

| レビュー | 特徴 |
|---|---|
| **ウォークスルー** | 作成者が主催し、成果物を順に説明しながら参加者が誤りを指摘する |
| **インスペクション** | **モデレータ**（進行役）が主催し、役割と手順を明確に定めて行う公式なレビュー |
| **ラウンドロビン** | 参加者が持ち回りでレビュー責任者を務める |
| **ピアレビュー** | 同僚どうしで行うレビュー |
| **パスアラウンド** | 成果物を回覧して、各自がコメントする |

:::trap レビューは「人」ではなく「成果物」を評価する
レビューで見つけた誤りの数を、作成者の人事評価に使ってはいけません。誤りを隠すようになり、レビューの効果がなくなるからです。選択肢で狙われやすいポイントです。
:::

## 6. アジャイル開発と DevOps

### アジャイルの代表的な手法

**アジャイル開発** は、1〜4週間程度の短い反復期間で、「計画・設計・実装・テスト」を繰り返し、動くソフトウェアを少しずつリリースしていく開発手法の総称です。

#### スクラム

| 用語 | 意味 |
|---|---|
| **プロダクトオーナー** | プロダクトの価値を最大化する責任者。プロダクトバックログの優先順位を決める |
| **スクラムマスター** | スクラムが正しく実践されるよう支援する。チームの障害を取り除く |
| **開発者（開発チーム）** | 実際にプロダクトを作る。自己組織化されたチーム |
| **スプリント** | 1か月以内の固定された反復期間 |
| **プロダクトバックログ** | プロダクトに必要な機能などを優先順位順に並べた一覧 |
| **スプリントバックログ** | 今回のスプリントで実施する項目と作業の計画 |
| **デイリースクラム** | 毎日15分程度で行う短い打合せ |
| **スプリントレビュー** | スプリントの成果物を関係者に見せ、フィードバックを得る |
| **スプリントレトロスペクティブ** | チームの進め方を振り返り、改善策を決める |

#### XP（エクストリームプログラミング）のプラクティス

- **ペアプログラミング**：2人1組で、1人がコードを書き、もう1人がその場でレビューする。
- **テスト駆動開発（TDD）**：**先にテストケースを書き**、そのテストに合格するようにコードを書く。
- **リファクタリング**：外部から見た動作を変えずに、プログラムの内部構造を改善する。
- **継続的インテグレーション（CI）**：コードの変更を頻繁に統合し、自動でビルド・テストする。

### DevOps と CI/CD

- **DevOps**：開発（Development）と運用（Operations）が協力し、ツールを活用して、迅速かつ安全にリリースを繰り返す考え方。
- **CI/CD**：継続的インテグレーション／継続的デリバリ（デプロイ）。ビルド・テスト・リリースを自動化するパイプラインを作る。
- **バージョン管理**：Git などで、ソースコードの変更履歴を管理する。
- **マイクロサービスアーキテクチャ**：システムを小さな独立したサービスの集まりとして構築し、API で連携させる。サービスごとに独立して開発・リリースできる。

## 7. 見積り・保守・知的財産の活用

### ソフトウェアの規模・工数見積り

| 手法 | 内容 |
|---|---|
| **ファンクションポイント法（FP法）** | 外部入力・外部出力・内部論理ファイル・外部インタフェースファイル・外部照会の **機能の数と複雑さ** から規模を見積もる。利用者から見た機能で測るので、開発言語に依存しない |
| **COCOMO** | 見積もったプログラムの規模（ステップ数）に、補正係数を掛けて工数を算出する |
| **類推見積法** | 過去の類似プロジェクトの実績を基に見積もる |
| **ボトムアップ見積法** | 作業を細かく分け、それぞれの見積りを積み上げる |
| **プログラムステップ法（LOC法）** | ソースコードの行数で規模を見積もる |

### 保守・リバースエンジニアリング

- **保守の種類**：是正保守（障害の修正）、適応保守（環境変化への対応）、完全化保守（性能や保守性の改善）、予防保守（潜在的な障害を事前に修正）。
- **リバースエンジニアリング**：既存のソフトウェアを解析して、仕様や設計を明らかにする。
- **リエンジニアリング**：リバースエンジニアリングで得た仕様を基に、新しいシステムを作り直す。

## 8. 過去問（令和2〜6年度）で問われた発展テーマ

### 設計・分析の手法

- **CRUD マトリクス**：縦に機能（業務処理）、横にデータ（エンティティ）を並べ、各機能がデータに対して **C**reate（生成）・**R**ead（参照）・**U**pdate（更新）・**D**elete（削除）のどれを行うかを記入した表。データを誰も作成していない、誰も参照していない、などの設計の漏れを発見できる。
- **データ中心アプローチ（DOA）**：業務手順よりも **変化しにくいデータ** を中心にシステムを設計する考え方。データを先にモデル化し、処理はその後で設計する（令和3年度秋期 午後問8）。
- **FTA（故障の木解析）**：好ましくない事象（トップ事象：例「ブレーキが効かない」）を頂点に置き、その **原因を AND・OR の論理記号で木の形に分解** していく（トップダウン）分析手法。
- **FMEA（故障モード影響解析）**：部品やプロセスの **故障の起こり方（故障モード）** を1つずつ洗い出し、それがシステム全体にどんな影響を与えるかを分析する（ボトムアップ）。
- **ローコード開発・ノーコード開発**：用意された部品やテンプレートを **GUI の操作で組み合わせて**、プログラムをほとんど（または全く）書かずにアプリケーションを開発する。

### ソフトウェアの品質特性（JIS X 25010）

| 品質特性 | 意味 |
|---|---|
| 機能適合性 | 必要な機能がそろい、正しく動くか |
| 性能効率性 | 応答時間や資源の使用量は適切か |
| 互換性 | 他の製品と共存・連携できるか |
| **使用性** | 利用者が **使い方を理解し、効率よく満足して使えるか**（例：「4時間の研修を受ければ、新しい画面を操作できる」） |
| 信頼性 | 故障しにくく、障害から回復できるか |
| セキュリティ | 不正なアクセスから守られているか |
| 保守性 | 修正や改良がしやすいか |
| 移植性 | 別の環境に移しやすいか |

### オブジェクト指向設計の補足

- **関連・集約・コンポジション**：クラス間の関係。**集約** は全体と部分の関係（部分は単独でも存在できる）、**コンポジション** は全体が消えると部分も消える強い集約。
- **委譲**：あるオブジェクトが、処理の一部を別のオブジェクトに任せること。継承を使わずに機能を再利用できる。
- **インタフェース・抽象クラス**：メソッドの名前（型）だけを決め、中身はサブクラスで実装する。新しい種類の部品を追加しても、呼び出す側を変えずに済む。

| デザインパターン | 内容 |
|---|---|
| **Observer** | あるオブジェクトの状態が変化したとき、それを **登録している複数のオブジェクトに自動的に通知** する（令和6年度春期 午後問8：ダッシュボードの表示更新） |
| **Singleton** | クラスのインスタンスが **1つだけ** であることを保証する |
| **Factory Method** | インスタンスの生成をサブクラスに任せる |
| **Adapter** | インタフェースの合わない既存クラスを、変換して使えるようにする |
| **Bridge** | 「機能の種類」と「実装の種類」を別々のクラス階層に分け、それぞれ独立に追加できるようにする |
| **Strategy** | アルゴリズムを部品化して、実行時に切り替えられるようにする |
| **Composite** | 部分と全体（フォルダとファイルなど）を同じように扱えるようにする |

### 並行処理・ノンブロッキング I/O

- **マルチスレッド**：1つのプログラムの中で複数のスレッドを並行して動かす。時間のかかる処理（通信など）を別スレッドで行えば、画面が固まらない。ただし、複数のスレッドが同じデータを更新するときは **排他制御**（第5章）が必要（令和5年度秋期 午後問8）。
- **ノンブロッキング I/O**：入出力の完了を **待たずに** 次の処理を進め、完了したら通知（イベント）を受けて続きを処理する方式。少ないスレッドで多数の接続を処理できる（令和3年度春期 午後問8）。

### バージョン管理（令和5年度春期 午後問8）

- **集中型**：1つの中央リポジトリでソースを管理する（Subversion など）。
- **分散型**：各開発者のローカル環境に、**全履歴を含むリポジトリの完全な複製** を持つ（**Git** など）。ネットワークにつながっていなくても履歴の確認やコミットができる。
- **ブランチ**：開発の流れを枝分かれさせる仕組み。新機能ごとにブランチを作って開発し、完成したら **マージ**（統合）する。リリース用のブランチ（main など）は常に動く状態に保つ、という運用ルールを決めることが多い。
- **コンフリクト（競合）**：複数の人が同じ箇所を変更してマージしたときに起きる衝突。手作業で解決する。
- **プルリクエスト**：ブランチの変更をマージする前に、レビューを依頼する仕組み。

### アジャイルの補足

**アジャイルソフトウェア開発宣言** は、次の4つの価値を示しています（右も価値があるが、左により価値をおく）。

- **プロセスやツール** よりも **個人と対話** を
- **包括的なドキュメント** よりも **動くソフトウェア** を
- **契約交渉** よりも **顧客との協調** を
- **計画に従うこと** よりも **変化への対応** を

- **ベロシティ**：1回のスプリントでチームが完了させた作業量（ストーリーポイントの合計）。次のスプリントの計画に使う。
- **リーンソフトウェア開発**：トヨタ生産方式の考え方をソフトウェア開発に応用したもの。**ムダの排除** を重視し、**バリューストリームマッピング**（開発のプロセスと所要時間・待ち時間を可視化して、ボトルネックを見つける）などの手法を使う。

### 共通フレームの補足

- **検証（Verification）**：成果物が、前の工程で決めた **仕様どおりに作られているか** を確認する。
- **妥当性確認（Validation）**：成果物が、利用者の **本当のニーズや使用目的を満たしているか** を確認する。
- **トレーサビリティ**：要件 → 設計 → プログラム → テストの対応関係を追跡できること。要件の漏れや、変更の影響範囲がわかる。

:::sum
- V字モデル：要件定義↔運用テスト、外部設計↔システムテスト、内部設計↔結合テスト、プログラム設計↔単体テスト。
- 非機能要件＝性能・可用性・セキュリティなど。DFD はデータの流れ（処理順序は表さない）。
- シーケンス図は時間順、ステートマシン図は状態変化。強度は機能的、結合度はデータ結合が最良。
- 判定条件網羅＝分岐の真偽、複数条件網羅が最も厳しい。限界値分析は境界の両側を選ぶ。
- スタブは下位の代役、ドライバは上位の代役。回帰テストは変更の悪影響の確認。
- スクラム：PO が優先順位、スクラムマスターが支援。TDD はテストが先。FP法は機能の数で規模を見積もる。
:::
