## 1. ITサービスマネジメントの枠組み

- **ITIL**：ITサービスマネジメントの **ベストプラクティス（成功事例）** をまとめた書籍群。英国政府が作成した。最新の ITIL 4 では「サービスバリューシステム（SVS）」として、価値の共創を重視している。
- **JIS Q 20000（ISO/IEC 20000）**：ITサービスマネジメントシステム（SMS）の **要求事項** を定めた規格。認証の基準になる。
- **PDCAサイクル**：計画（Plan）→実行（Do）→点検（Check）→処置（Act）を繰り返して、サービスを継続的に改善する。

## 2. サービスレベル管理

- **SLA（Service Level Agreement：サービスレベル合意書）**：サービス提供者と利用者（顧客）の間で、**サービスの内容と品質の目標値** を合意した文書。稼働率、応答時間、障害時の復旧時間、問合せ受付時間などを数値で定める。
- **SLM（サービスレベル管理）**：SLA を合意し、実績を監視・報告し、改善を続けるプロセス。
- **OLA（運用レベル合意書）**：サービス提供者の **組織内部の部門間** で結ぶ合意。
- **UC（Underpinning Contract：裏付け契約）**：サービス提供者が **外部の供給者** と結ぶ契約。
- **SLO**：SLA の中の個々のサービスレベル目標値。

:::calc SLA の稼働率から許容停止時間を求める
「月間稼働率 99.9%以上」を合意した。1か月を30日とすると、許容される停止時間は？
30日 × 24時間 ＝ 720時間。停止してよい割合 ＝ 0.1% → 720 × 0.001 ＝ **0.72時間 ＝ 約43分**
計画停止（メンテナンス）を稼働率の計算に含めるかどうかも、SLA で決めておく必要があります。
:::

## 3. インシデント管理と問題管理

- **インシデント**：サービスの計画外の中断や、品質の低下（サーバが止まった、画面の表示が遅い）。
- **サービス要求**：パスワードの再設定やソフトウェアの使い方の質問など、障害ではない定型的な依頼。**サービス要求管理** で扱う。
- **優先度**：**影響度**（業務への影響の大きさ）と **緊急度**（解決までに許される時間）を組み合わせて決める。
- **エスカレーション**：自分たちで解決できない場合に、より専門的な担当（**機能的エスカレーション**）や上位の管理者（**階層的エスカレーション**）に引き継ぐこと。

## 4. 変更管理・リリース管理・構成管理

- **変更管理**：サービスやシステムへの変更を、**リスクと影響を評価してから承認** し、計画的に実施するプロセス。変更の申請は **RFC（変更要求）** で行い、**CAB（変更諮問委員会）** が評価する。緊急の変更は ECAB（緊急変更諮問委員会）が扱う。
- **リリース管理及び展開管理**：承認された変更を、本番環境に確実に展開（リリース）する。展開前のテスト、展開の計画、失敗時の **切り戻し（ロールバック）** 計画を立てる。
- **構成管理**：サービスを構成する要素（**構成品目：CI**）――ハードウェア、ソフトウェア、ドキュメントなど――の情報と相互関係を **CMDB（構成管理データベース）** に記録し、常に最新の状態に保つ。

## 5. サービスデスク

**サービスデスク** は、利用者からの問合せやインシデントの報告を受け付ける **単一の窓口（SPOC：Single Point Of Contact）** です。

| 形態 | 内容 |
|---|---|
| **ローカルサービスデスク** | 利用者の拠点ごとに設置する |
| **中央サービスデスク** | 1か所に集約する。効率がよい |
| **バーチャルサービスデスク** | 担当者は各地に分散しているが、ネットワークで1つの窓口に見せる |
| **フォロー・ザ・サン** | 時差のある複数の拠点で引き継ぎながら、24時間対応する |

- **FAQ・チャットボット**：利用者自身が解決できるようにして（セルフヘルプ）、問合せを減らす。
- **一次解決率**：最初の窓口で解決できた割合。サービスデスクの評価指標。

## 6. 可用性管理・容量管理・サービス継続管理

- **可用性管理**：合意した可用性（稼働率）を達成するために、冗長化や保守を計画する。MTBF・MTTR の考え方は第4章を参照。
- **容量・能力管理（キャパシティ管理）**：CPU・メモリ・ネットワークの使用状況を監視し、**将来の需要を予測** して、必要な容量を計画する。
- **サービス継続管理**：災害などの重大な事態でも、合意したレベルでサービスを継続・復旧できるようにする。
- **BCP（事業継続計画）**：災害やシステム障害が起きても、重要な業務を継続・早期復旧するための計画。
- **RTO（目標復旧時間）**：障害発生から **いつまでに** 復旧させるか。**RPO（目標復旧時点）**：障害発生時に、**どの時点まで** のデータを復旧させるか（＝どれだけのデータ損失を許容するか）。

:::point RTO と RPO の区別
RTO は「Time（どれだけ早く戻すか）」、RPO は「Point（どの時点のデータまで戻すか）」。RPO を「直前」にするなら、リアルタイムのレプリケーション（複製）が必要になります。
:::

## 7. サービスの運用

- **ジョブ管理**：バッチ処理などのジョブの実行スケジュールを管理し、自動実行・監視する。
- **バックアップ**：フル・差分・増分（第5章）。バックアップの媒体を **遠隔地に保管** して災害に備える。
- **監視**：死活監視（ping などで生きているか確認）、性能監視、ログ監視。
- **SRE（サイトリライアビリティエンジニアリング）**：ソフトウェアエンジニアリングの手法でシステム運用の信頼性を高める考え方。**エラーバジェット**（SLO で許容される失敗の量）の範囲内で新機能のリリースを進める。

## 8. ファシリティマネジメント

**ファシリティマネジメント** とは、コンピュータを設置する建物や設備を、最適な状態に保つ管理活動です。

| 設備 | 内容 |
|---|---|
| **UPS（無停電電源装置）** | 停電時にバッテリーから **一時的に** 電力を供給する。その間にシステムを安全に停止させる |
| **自家発電装置** | 長時間の停電に備えて発電する（UPS とセットで使う） |
| **サージ保護** | 落雷などによる異常な電圧（サージ）から機器を守る |
| **免震・耐震** | 地震の揺れを伝えにくくする／揺れに耐える |
| **データセンタ** | サーバを安全に運用するための専用施設。空調、電源、セキュリティが整っている |

- **PUE**：データセンタ全体の消費電力 ÷ IT機器の消費電力。**1に近いほど省エネ**。
- **グリーンIT**：IT機器の省エネや、ITを使った社会全体の環境負荷低減。

:::sum
- SLA は提供者と顧客の合意、OLA は内部部門間、UC は外部供給者との契約。
- インシデント管理＝迅速な回復（暫定対応可）、問題管理＝根本原因の究明と再発防止。
- 変更は RFC で申請し CAB が評価。構成情報は CMDB。サービスデスクは単一窓口（SPOC）。
- RTO は復旧までの時間、RPO はどの時点のデータまで戻すか。
- UPS は一時的な電力供給、長時間は自家発電。PUE は1に近いほど良い。
:::
