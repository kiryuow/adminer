## 1. データベースの基本

### データモデル

- **関係データモデル（リレーショナルモデル）**：データを表で表し、表どうしを共通の値で関連付ける。現在の主流。
- **階層型モデル**：データを木構造（親子関係）で表す。
- **ネットワーク型モデル**：データを網目状につなぐ。

### 3層スキーマ

DBの構造を3つの視点で定義し、利用者の見え方と物理的な格納方法を切り離す考え方です。

| スキーマ | 内容 |
|---|---|
| **外部スキーマ** | 利用者やプログラムから見たデータの形（**ビュー**） |
| **概念スキーマ** | DB全体の論理的な構造（表の定義） |
| **内部スキーマ** | ディスク上の物理的な格納方法 |

### キーの種類

| キー | 意味 |
|---|---|
| **候補キー** | 行を一意に特定できる、必要最小限の列の組合せ。複数ある場合もある |
| **主キー** | 候補キーの中から1つ選んだもの。**重複不可・NULL不可**（一意性制約・非NULL制約） |
| **外部キー** | 他の表の主キーを参照する列。参照先に存在しない値は入れられない（**参照制約**） |
| **複合キー（連結キー）** | 複数の列を組み合わせたキー |

:::note NULL（ナル）とは
「値が存在しない・不明」を表す特別な状態です。0や空文字とは違います。SQLで NULL かどうかを調べるときは「= NULL」ではなく「**IS NULL**」と書きます。
:::

## 2. E-R 図（概念データモデル）

**E-R図** は、データベースを設計する前に、管理対象（**エンティティ**：実体）と、それらの関係（**リレーションシップ**）を図で表したものです。

- **エンティティ**：管理したい「もの」や「こと」（社員、部署、受注など）。長方形で表す。
- **属性**：エンティティが持つ項目（社員番号、氏名など）。
- **カーディナリティ（多重度）**：関係の数の対応。**1対1、1対多、多対多**。

:::point 多対多は連関エンティティで分解する
「学生」と「科目」は多対多（1人の学生が多くの科目を履修し、1つの科目を多くの学生が履修）です。関係データベースでは多対多を直接表せないので、間に「**履修**」という表（連関エンティティ）を作り、「学生 1対多 履修 多対1 科目」に分解します。午後問6で頻出の考え方です。
:::

## 3. 正規化

### 正規化とは

**正規化** とは、表を適切に分割して、**データの重複をなくし、更新時の矛盾（更新時異状）を防ぐ** ことです。例えば、受注表の各行に顧客の住所を書いておくと、住所が変わったとき全行を直さなければならず、直し漏れで矛盾が起きます。

### 関数従属

**関数従属** とは、「Aの値が決まれば、Bの値がただ1つに決まる」関係で、**A → B** と書きます。例：社員番号 → 氏名（社員番号が決まれば氏名が1つに決まる）。正規化はこの関数従属を手がかりに行います。

<div class="fig" markdown="1"><div class="fig-t">第7章② 正規化のステップ</div><div class="fig-b" markdown="1">

| 段階 | 条件 | やること |
|---|---|---|
| **非正規形** | 1つのセルに複数の値（繰返し項目）がある | ― |
| **第1正規形** | すべての項目が単一の値（**繰返し項目がない**） | 繰返し項目を別の行に分ける |
| **第2正規形** | 第1正規形 ＋ **部分関数従属がない** | 主キーの **一部** だけで決まる項目を別表に分ける |
| **第3正規形** | 第2正規形 ＋ **推移的関数従属がない** | 主キー以外の項目で決まる項目を別表に分ける |

</div></div>

:::calc 正規化の具体例
受注表（**受注番号, 商品コード**, 受注日, 顧客コード, 顧客名, 商品名, 数量）　※太字が主キー
**①部分関数従属を見つける**：受注番号 → 受注日, 顧客コード, 顧客名 ／ 商品コード → 商品名。主キーの一部だけで決まるので、別表に分ける（第2正規形）。
　受注（**受注番号**, 受注日, 顧客コード, 顧客名）／商品（**商品コード**, 商品名）／受注明細（**受注番号, 商品コード**, 数量）
**②推移的関数従属を見つける**：受注番号 → 顧客コード → 顧客名。主キー以外の顧客コードで顧客名が決まるので、別表に分ける（第3正規形）。
　受注（**受注番号**, 受注日, 顧客コード）／顧客（**顧客コード**, 顧客名）
:::

:::note ボイス・コッド正規形（BCNF）
第3正規形よりさらに厳しく、「すべての関数従属 A → B で、A が候補キーを含む」状態です。応用情報ではまれに出題されます。
:::

## 4. SQL

**SQL** は、関係データベースを操作するための言語です。

### データ定義（DDL）とデータ操作（DML）

| 種類 | 主な命令 | 用途 |
|---|---|---|
| DDL（定義） | CREATE TABLE / CREATE VIEW / DROP / ALTER | 表やビューを作る・削除する・変更する |
| DML（操作） | SELECT / INSERT / UPDATE / DELETE | データを検索・追加・更新・削除する |
| DCL（制御） | GRANT / REVOKE / COMMIT / ROLLBACK | 権限の付与・取消し、トランザクションの確定・取消し |

### SELECT 文の基本

```
SELECT 部署コード, AVG(給与) AS 平均給与     -- ④取り出す列
  FROM 社員                                   -- ①どの表から
 WHERE 給与 >= 200                            -- ②行を絞り込む
 GROUP BY 部署コード                           -- ③グループにまとめる
HAVING AVG(給与) > 300                        -- ③'グループを絞り込む
 ORDER BY 平均給与 DESC                       -- ⑤並べ替え（DESC:降順）
```

:::point WHERE と HAVING の違い
**WHERE** は「グループ化する前の **行** 」を絞り込み、**HAVING** は「GROUP BY でまとめた後の **グループ** 」を絞り込みます。集約関数（SUM, AVG, COUNT, MAX, MIN）を条件に使うときは HAVING です。
:::

### よく使う述語・関数

| 書き方 | 意味 |
|---|---|
| BETWEEN 100 AND 200 | 100以上200以下 |
| IN ('D01', 'D02') | いずれかに一致 |
| LIKE '山%' | 「山」で始まる（% は0文字以上の任意の文字列、_ は任意の1文字） |
| IS NULL | 値が NULL |
| COUNT(*) | 行数（NULL を含む）。COUNT(列) は NULL を数えない |
| DISTINCT | 重複を除く |

### 表の結合

```
SELECT 社員.氏名, 部署.部署名
  FROM 社員 INNER JOIN 部署
    ON 社員.部署コード = 部署.部署コード
```

- **内部結合（INNER JOIN）**：両方の表で結合条件が一致する行だけを取り出す。
- **左外部結合（LEFT OUTER JOIN）**：左の表のすべての行を残し、右の表に一致する行がなければ NULL で埋める。「受注がない顧客も一覧に出したい」ときに使う。

### 副問合せ（サブクエリ）

SELECT 文の中に、さらに SELECT 文を入れる書き方です。

```
-- 平均より給与が高い社員
SELECT 氏名 FROM 社員
 WHERE 給与 > (SELECT AVG(給与) FROM 社員)

-- 受注が1件もない顧客（相関副問合せ）
SELECT 顧客名 FROM 顧客 C
 WHERE NOT EXISTS (SELECT * FROM 受注 J WHERE J.顧客コード = C.顧客コード)
```

- **EXISTS**：副問合せの結果が1行以上あれば真。**相関副問合せ** は外側の行ごとに内側を実行する。

### 関係代数（集合演算）

| 演算 | 内容 |
|---|---|
| **選択** | 条件に合う **行** を取り出す（WHERE） |
| **射影** | 指定した **列** を取り出す（SELECT 列名） |
| **結合** | 共通の列で2つの表をつなぐ（JOIN） |
| 和・差・積 | 2つの表の行の和集合（UNION）・差集合（EXCEPT）・積集合（INTERSECT） |
| 直積 | 2つの表のすべての行の組合せ |

### ビューとインデックス

- **ビュー**：SELECT 文の結果を、仮想的な表として定義したもの。利用者に必要な列だけ見せる（セキュリティ）、複雑な問合せを簡単にするなどに使う。
- **インデックス（索引）**：検索を速くするための仕組み。B<sup>+</sup>木がよく使われる。検索は速くなるが、更新時にインデックスも更新するので **更新は遅くなる**。

## 5. トランザクション管理

### トランザクションと ACID 特性

**トランザクション** とは、「これ以上分けられない一連の処理のまとまり」です。例えば銀行振込の「A口座から引く」と「B口座に足す」は、両方成功するか両方取り消すかのどちらかでなければなりません。トランザクションは次の **ACID特性** を満たす必要があります。

<div class="fig"><div class="fig-t">第7章③ ACID 特性</div><div class="fig-b"><div class="cards" style="--n:4">
<div class="card c1"><b>Atomicity 原子性</b>全部成功（コミット）か、全部取消し（ロールバック）のどちらか</div>
<div class="card c2"><b>Consistency 一貫性</b>処理の前後でデータの整合性が保たれる</div>
<div class="card c3"><b>Isolation 独立性</b>同時に実行しても、互いに影響しない（順に実行したのと同じ結果）</div>
<div class="card c4"><b>Durability 永続性</b>コミットした結果は、障害が起きても失われない</div>
</div></div></div>

### 排他制御（ロック）

複数のトランザクションが同じデータを同時に更新すると、片方の更新が消える（**ロストアップデート**）などの問題が起きます。これを防ぐのが **ロック** です。

| ロック | 意味 | 他のトランザクションは |
|---|---|---|
| **共有ロック**（読取り用） | データを読む間かける | 読取りは可、更新は不可 |
| **専有ロック**（排他ロック・更新用） | データを更新する間かける | 読取りも更新も不可 |

- **2相ロック方式**：必要なロックをすべてかけ終わるまでロックを解除しない（ロックをかける相 → 解除する相）。これで直列化可能性が保証される。
- **デッドロック**：トランザクションどうしが互いのロック解除を待ち合う状態（第5章と同じ）。DBMS は検出して、一方をロールバックする。
- **ロックの粒度**：ロックをかける単位（表・ページ・行）。粒度が **細かい** ほど同時実行性は高いが、ロック管理の負荷が大きい。
- **楽観的ロック**：ロックをかけずに処理し、更新時に他者が変更していないかを確認する方式。

### 障害回復

DBMS は、更新の前後のデータを **ログ（ジャーナル）** に記録しておき、障害時に使います。

| 回復処理 | 使うもの | 場面 |
|---|---|---|
| **ロールバック（後退復帰）** | **更新前** ログ | トランザクションの途中で障害が起きたとき、処理を **取り消して** 開始前の状態に戻す |
| **ロールフォワード（前進復帰）** | バックアップ ＋ **更新後** ログ | ディスク障害のとき、バックアップを復元してから更新後ログで **やり直して** 障害直前の状態にする |

- **チェックポイント**：一定間隔で、メモリ上の更新内容をディスクに書き出す時点。システム障害時は、チェックポイント以降のログだけ処理すればよいので回復が速い。
- **2相コミット**：分散データベースで、複数のサイトの更新を整合させる方式。第1相で全サイトに「コミットできるか」を確認し、全員OKなら第2相でコミットを指示する。

## 6. データベースの応用

- **データウェアハウス**：業務データを時系列に蓄積し、意思決定の分析に使う大規模DB。
- **データマイニング**：大量のデータから、統計やAIで有用なパターンや規則性を見つけ出す。
- **OLAP**：データを多次元的に集計・分析する（ドリルダウン、スライスなど）。
- **NoSQL**：関係モデル以外のDB。**キーバリュー型**、**ドキュメント型**（JSONなど）、**列指向型**、**グラフ型**。大量データの高速処理や柔軟な構造に強い。
- **BASE特性**：NoSQL が重視する特性。ACID のような厳密な一貫性より、可用性を優先し「最終的に一貫すればよい（結果整合性）」と考える。
- **ビッグデータ**：量（Volume）・速度（Velocity）・多様性（Variety）が大きいデータ。
- **データレイク**：構造化・非構造化を問わず、生データをそのまま大量に蓄積する保存場所。
- **ブロックチェーン**：取引記録をハッシュ値でつないだブロックの鎖として、多数の参加者で分散管理する技術。改ざんが極めて困難。

## 7. 過去問（令和2〜6年度）で問われた発展テーマ

### 関係演算「商」

**商（÷）** は、「関係 S のすべての値と組み合わさっている、関係 R の値」を取り出す演算です。例えば R（社員, 資格）、S（資格）＝{基本情報, 応用情報} のとき、R ÷ S は「基本情報と応用情報の **両方** を持っている社員」になります。

### SQL の発展（午前・午後の両方で頻出）

:::calc CASE 式で縦の表を横に並べる
売上（部門, 期, 金額）から、部門ごとに上期・下期の売上を横に並べる。
```
SELECT 部門,
       SUM(CASE WHEN 期 = '上期' THEN 金額 ELSE 0 END) AS 上期売上,
       SUM(CASE WHEN 期 = '下期' THEN 金額 ELSE 0 END) AS 下期売上
  FROM 売上
 GROUP BY 部門
```
CASE 式は「条件に応じて値を変える」式です。GROUP BY と組み合わせて集計表を作るのが定番です。
:::

| 機能 | 内容 |
|---|---|
| **ウィンドウ関数** | 行をまとめずに、各行に集計結果や順位を付ける。`RANK() OVER (PARTITION BY 部門 ORDER BY 売上 DESC)` で部門ごとの売上順位、`SUM(売上) OVER (ORDER BY 月)` で累計を求める（令和5年度秋期 午後問6） |
| **再帰的な問合せ** | `WITH RECURSIVE` を使い、部品構成や組織の上下関係のような **階層構造** をたどる（令和6年度秋期 午後問6） |
| **外部キーの参照動作** | `FOREIGN KEY … REFERENCES 注文(注文番号) ON DELETE CASCADE` とすると、参照先（注文）の行を削除したとき、参照している行（注文明細）も **自動的に削除** される。`RESTRICT` なら参照されている行は削除できない |
| **制約** | `PRIMARY KEY`、`UNIQUE`（重複不可）、`NOT NULL`、`CHECK`（値の条件）、`FOREIGN KEY` |
| **更新可能なビュー** | 基本的に、**1つの表** から作られ、集約関数・GROUP BY・DISTINCT などを使っていないビューは、ビューを通して元の表を更新できる |
| **ストアドプロシージャ** | 一連の SQL 文をまとめて DBMS に保存しておき、アプリケーションから **名前を指定して呼び出す**。ネットワークの通信回数が減り、性能が向上する |
| **トリガ** | 表の更新などの操作を契機に、自動的に実行される処理 |
| **カーソル** | プログラムから SQL の結果を **1行ずつ** 取り出して処理するための仕組み |

### トランザクションの隔離性水準

同時に実行するトランザクションが、どこまで互いに影響し合うことを許すかの設定です。隔離性を高くするほど矛盾は起きにくくなりますが、待ちが増えて性能は下がります。

| 隔離性水準 | ダーティリード | ノンリピータブルリード | ファントムリード |
|---|---|---|---|
| READ UNCOMMITTED | 起こる | 起こる | 起こる |
| READ COMMITTED | 起こらない | 起こる | 起こる |
| REPEATABLE READ | 起こらない | 起こらない | 起こる |
| SERIALIZABLE（最も高い） | 起こらない | 起こらない | 起こらない |

- **ダーティリード**：他のトランザクションが **コミットしていない** 更新を読んでしまう。
- **ノンリピータブルリード**：同じ行を2回読むと、間に他者が更新したため値が変わっている。
- **ファントムリード**：同じ条件で2回検索すると、間に他者が追加した行が現れる。

| トランザクションの状態 | 回復処理 |
|---|---|
| チェックポイント **より前** にコミット済み | 何もしない（ディスクに反映済み） |
| チェックポイント **より後**、障害発生 **より前** にコミット | **ロールフォワード**（更新後ログでやり直す） |
| 障害発生時点で **コミットしていない** | **ロールバック**（更新前ログで取り消す） |

### データ管理の役割

- **DA（データ管理者）**：全社的な視点から、データの意味や名称の **標準化**、データモデルの管理を行う。
- **DBA（データベース管理者）**：個々のデータベースの物理設計、性能の監視・チューニング、バックアップ、アクセス権限の設定など、**運用と技術面** を担当する。
- **マルチテナント**：1つのシステム（データベース）を複数の利用企業（テナント）で共有する方式。テナントごとにデータを分離する方法として、「テナントIDの列で区別する」「テナントごとにスキーマを分ける」「データベースを分ける」などがある（令和6年度春期 午後問6）。
- **グラフ指向データベース**：データを「ノード」と「関係（エッジ）」で表す NoSQL。SNS の友人関係など、つながりの探索に強い。

### スーパータイプとサブタイプ（令和7年度秋期 午後問6）

複数のエンティティに共通する属性を **スーパータイプ** にまとめ、それぞれに固有の属性を **サブタイプ** に分けるモデル化の方法です。例えば「顧客」をスーパータイプとし、「個人顧客」（生年月日）と「法人顧客」（資本金）をサブタイプにします。

- サブタイプの主キーは、スーパータイプの主キーと同じにする（スーパータイプを参照する外部キーにもなる）。
- **排他的サブタイプ**：1つの顧客は個人か法人のどちらか一方にしか属さない。**共存的サブタイプ**：同時に複数のサブタイプに属せる。
- 表への実装方法には、①スーパータイプとサブタイプを別々の表にする、②1つの表にまとめて区分の列で区別する、などがあり、NULL の多さや結合の手間で選ぶ。

:::sum
- 主キーは重複不可・NULL不可。外部キーは参照制約。NULL の判定は IS NULL。
- 第1正規形＝繰返しなし、第2＝部分関数従属なし、第3＝推移的関数従属なし。
- WHERE は行、HAVING はグループを絞る。LEFT OUTER JOIN は左表を全件残す。
- ACID：原子性・一貫性・独立性・永続性。共有ロックは読取り可、専有ロックは一切不可。
- ロールバックは更新前ログで取消し、ロールフォワードはバックアップ＋更新後ログでやり直し。
- NoSQL は BASE（結果整合性）。インデックスは検索が速く更新が遅くなる。
:::
