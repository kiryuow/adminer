## 12. システム開発技術

### 要件定義・設計

| 用語 | 意味 |
|---|---|
| 要件の種類 | 性能要件、セキュリティ要件、移行要件、運用要件、保守要件、品質要件など。非機能要件として明確にする |
| 運用シナリオ・利用の状況 | システムが誰に、どんな場面で、どう使われるかを具体的に記述したもの |
| イネーブリングシステム | 開発・テスト・運用を支えるためのシステム（開発環境、テスト設備など） |
| 双方向のトレーサビリティ | 要件から成果物へ、成果物から要件へ、の両方向に対応をたどれること。**トレーサビリティマトリクス** で管理する |
| アシュアランスケース | システムが安全・安心であることを、主張と根拠を構造的に示して説明する文書 |
| 外部一貫性・内部一貫性 | 上位の文書と矛盾がないこと ／ その文書の中で矛盾がないこと（レビューの観点） |
| 垂直型・水平型プロトタイプ | 一部の機能を深く作り込む ／ 多くの機能の画面だけを浅く作る |
| コンテキストダイアグラム | 対象システムを1つの円で表し、外部実体とのデータの流れだけを描いたDFDの最上位の図 |
| ミニスペック | DFDの最下位のプロセスの処理内容を記述したもの |
| 段階的詳細化 | 大まかな機能から、少しずつ詳しく分解していく設計の進め方 |
| エピック・ユーザーストーリー | 大きな要求のかたまり ／ 利用者の視点で書いた要求の単位（エピックを分割して作る） |
| ペトリネット | 並行して動く処理の同期や競合を、プレース・トランジション・トークンで表すモデル |
| ゴール指向要求分析（KAOS、i*） | 目標（ゴール）を分解して、要求を導き出す手法 |
| サービスメッシュ | マイクロサービス間の通信を、専用の層（プロキシ）で一元的に制御する仕組み（Istio） |
| サーキットブレーカー | 呼出し先のサービスが故障しているとき、呼出しを一時的に遮断して障害の連鎖を防ぐ仕組み |
| サーバレスアーキテクチャ | サーバ管理をクラウド事業者に任せ、イベント駆動の関数でシステムを構成する |
| クリーンアーキテクチャ | 業務ロジックを中心に置き、画面やDBなどの外側の技術に依存しないように層を分ける設計 |
| ドメイン駆動設計の用語 | **ドメインモデル**（業務の概念のモデル）、**ユビキタス言語**（開発者と業務担当者が共通に使う言葉）、**値オブジェクト**、**コンテキストマップ** |
| 構造化設計の図 | **NS図**（箱の入れ子で構造化プログラムを表す）、**HIPO**（階層図と入力・処理・出力の図）、**PAD・SPD・HCPチャート**（構造化プログラムの図式） |
| ジャクソン法・ワーニエ法 | 入出力のデータ構造からプログラムの構造を導く設計手法 |
| STS分割 | 処理をSource（入力）・Transform（変換）・Sink（出力）に分けるモジュール分割 |
| TR分割・共通機能分割 | 処理の種類（トランザクション）ごとに分ける ／ 共通する機能を独立させる |
| モジュールの制御領域・影響領域 | あるモジュールから呼び出される範囲 ／ ある判定の影響を受ける範囲。影響領域は制御領域に含まれるのがよい |
| COTS | 市販の既製品のソフトウェア（パッケージ） |
| レガシーラッピング | 古いシステムをそのまま包み込み、新しいインタフェースで使えるようにする |
| GoF | オブジェクト指向の23のデザインパターンをまとめた4人の著者。デザインパターンの代名詞 |
| 一事実一箇所 | 同じ事実（データ）は1か所だけに持つ、というデータ設計の原則 |

### 実装・テスト・導入・保守

| 用語 | 意味 |
|---|---|
| アスペクト指向プログラミング | ログ出力など、多くの処理に横断的に関わる機能を分離して記述する手法 |
| サイクロマティック複雑度 | プログラムの分岐の多さを表す指標（辺の数 − 節点の数 ＋ 2）。大きいほどテストが難しい |
| コードインスペクション・ピアコードレビュー | ソースコードを対象とした公式なレビュー ／ 同僚どうしのレビュー |
| テストオラクル | テスト結果が正しいかを判断するための基準（期待値） |
| テスト密度・欠陥密度 | 規模あたりのテスト項目数 ／ 規模あたりの欠陥数。品質の評価に使う |
| 実験計画法（直交表） | 少ないテストケースで、因子の組合せを効率よく網羅する手法 |
| ミューテーションテスト | プログラムにわざと小さな変更（変異）を加え、テストがそれを検出できるかでテストの質を評価する |
| テストベッド | テストを行うための環境（ハードウェア、ソフトウェア、データ） |
| カナリアリリース | 新しいバージョンを一部の利用者にだけ先に公開し、問題がなければ徐々に広げる |
| ブルーグリーンデプロイメント | 本番環境を2系統用意し、新バージョンの系統に一気に切り替える。問題があればすぐ戻せる |
| 移行リハーサル | 本番の移行の前に、手順や所要時間を確認するための予行演習 |
| 検収・受入れ基準 | 発注者が成果物を検査して受け取ること ／ その合格の基準 |
| カークパトリックの4段階モデル | 教育の効果を、反応（満足度）→ 学習（理解度）→ 行動（職場での実践）→ 結果（業績）の4段階で評価する |
| 利用者用文書類 | ウィザード（手順を対話形式で案内）、チュートリアル、オンラインヘルプ、マニュアル |
| オンサイト保守・リモート保守 | 技術者が現地に行って保守する ／ ネットワーク経由で遠隔から保守する |
| 保守の種類の補足 | 改良保守（機能追加・性能改良）、予防保守、是正保守、適応保守 |
| 廃棄 | 廃棄計画を立て、関係者に通知し、データを安全に保持・消去してシステムを停止する |

## 13. ソフトウェア開発管理技術

| 用語 | 意味 |
|---|---|
| 段階的モデル・進展的モデル | 機能を段階的に分けて順に開発・リリースする（インクリメンタル） ／ 要求の変化に合わせて全体を繰り返し改良する（エボリューショナリ） |
| ソフトウェアプロダクトライン | 共通部分を資産として再利用し、多数の派生製品を効率よく開発する手法 |
| MLOps | 機械学習モデルの開発・デプロイ・監視・再学習を継続的に回すための仕組み |
| アジャイルの12の原則 | アジャイル宣言の背後にある原則（顧客満足を最優先し、価値のあるソフトウェアを早く継続的に提供する、など） |
| インセプションデッキ | プロジェクト開始時に、目的や範囲などをチームと関係者で共有する10の質問 |
| INVEST | 良いユーザーストーリーの条件：独立・交渉可能・価値がある・見積り可能・小さい・テスト可能 |
| プランニングポーカー | 数字の書かれたカードを全員で同時に出して、作業の規模を見積もる手法 |
| タイムボックス | 作業の期間をあらかじめ固定し、その中でできることを行う考え方 |
| バーンダウンチャート | 残りの作業量を縦軸、時間を横軸にとったグラフ。進捗を見える化する |
| モブプログラミング | チーム全員で1台の画面を見ながら、一緒にプログラムを書く |
| KPT | 振り返りで、Keep（続けること）・Problem（問題）・Try（次に試すこと）を整理する手法 |
| 大規模スクラム | LeSS、Scrum of Scrums、SAFeなど、複数のチームでスクラムを行う枠組み |
| インクリメント | スプリントで完成した、リリース可能なプロダクトの増分 |
| カオスエンジニアリング | 本番環境にわざと障害を起こし、システムの回復力を確かめて改善する手法 |
| Four Keys | 開発チームの能力を測る4指標：デプロイの頻度、変更のリードタイム、変更障害率、平均修復時間 |
| オブザーバビリティ（可観測性） | ログ・メトリクス・トレースから、システムの内部状態を把握できること（OpenTelemetryは収集の標準） |
| DevSecOps | DevOpsの各段階にセキュリティ対策を組み込む考え方 |
| マッシュアップ | 複数のWebサービスやAPIを組み合わせて、新しいサービスを作ること |
| ネイティブアプリ・ハイブリッドアプリ | 端末のOS向けに作られたアプリ ／ Web技術で作り、ネイティブアプリとして配布するアプリ |
| 形式手法・モデル検査 | 仕様を数学的に厳密に記述する（Z言語、VDM） ／ 状態をすべて調べて仕様を満たすか自動で検証する（SPIN） |
| JIS X 0160・0170 | ソフトウェア／システムのライフサイクルプロセスの規格（共通フレームの元になる国際規格） |
| プロセス修整（テーラリング） | 標準のプロセスを、組織やプロジェクトに合わせて調整すること |
| CMMI・プロセス能力水準 | 組織の開発プロセスの成熟度を5段階で評価するモデル（初期 → 管理された → 定義された → 定量的に管理された → 最適化している）。JIS X 33001 系も同様の評価の規格 |
| 専用実施権・通常実施権 | 特許を独占的に実施できる権利（特許権者も実施できない） ／ 独占的ではない実施の許諾 |
| ライセンサー・ライセンシー | 使用を許諾する側 ／ 許諾を受ける側 |
| DRM・コピーガード | デジタルコンテンツの不正コピーや利用を制限する技術（CPRM、AACSは録画・ブルーレイ向けの方式） |
| アクティベーション | ソフトウェアのライセンス認証。インストールした端末を登録して不正利用を防ぐ |
| ステージング環境 | 本番とほぼ同じ構成の、リリース前の最終確認用の環境 |
| ベースライン | 正式に承認され、以後の変更管理の基準となる成果物の状態 |

## 14. プロジェクトマネジメント

| 用語 | 意味 |
|---|---|
| ポートフォリオ・プログラム・プロジェクト | 組織の目標達成のため複数のプログラム・プロジェクトを一括管理 ／ 関連する複数のプロジェクトをまとめて管理 ／ 個別のプロジェクト |
| プロジェクトスポンサー | プロジェクトに資金や資源を提供し、支援する人（組織） |
| ビジネスケース | プロジェクトを実施する理由と、期待される価値・費用対効果をまとめた文書 |
| 変更管理委員会（CCB） | プロジェクトの変更要求を審査し、承認・却下する機関 |
| 得た教訓（教訓登録簿） | プロジェクトでうまくいったこと・失敗したことを記録し、今後に生かす文書 |
| ステークホルダー登録簿・分析 | 関係者の一覧と、その関心・影響力の分析（権力・関心度グリッドなど） |
| WBS辞書・100%ルール | WBSの各要素の詳細な説明 ／ 下位の要素の合計が上位の要素の作業の100%になるように分解する原則 |
| RBS | 資源ブレークダウンストラクチャ（必要な資源を種類別に分解）、または リスクブレークダウンストラクチャ（リスクを原因別に分類） |
| 見積り手法 | **類推見積り**（過去の類似プロジェクトから）、**パラメトリック見積り**（単価×数量などの統計的関係から）、**ボトムアップ見積り**（細かい作業を積み上げる）、**予備設定分析**（予備の量を決める） |
| CCPM（クリティカルチェーン） | 各作業の余裕を削り、プロジェクトの最後にまとめて **プロジェクトバッファ** を置く。合流する経路には **合流バッファ** を置く |
| マイルストーン | プロジェクトの重要な節目（所要期間0の目印） |
| 資源平準化・資源円滑化 | 資源の過剰な割当てをなくすよう作業をずらす（期間が延びることがある） ／ 余裕の範囲内でずらす（期間は延びない） |
| What-Ifシナリオ分析 | 「もしこの作業が遅れたら」などの仮定で、スケジュールへの影響を評価する |
| COCOMO II | COCOMOを改良した工数見積りモデル |
| コストベースライン | 承認された、時間軸に沿った予算の計画（PVの累積） |
| 品質コスト（COQ） | 品質に関わる費用。予防コスト・評価コスト（適合コスト）と、内部・外部の失敗コスト（不適合コスト） |
| 費用便益分析 | 対策の費用と、それによって得られる便益を比べて判断する |
| SOW（作業範囲記述書） | 調達する作業の範囲や内容を記述した文書 |
| プッシュ型・プル型コミュニケーション | 送り手から相手に送る（メール） ／ 受け手が必要なときに取りに行く（共有サイト） |
| メラビアンの法則 | 話し手の印象は、言葉の内容よりも、声のトーンや表情などの非言語情報の影響が大きい、という説 |

## 15. サービスマネジメント

| 用語 | 意味 |
|---|---|
| SLI | サービスレベルを測る指標（応答時間、稼働率など） |
| サービス可用性・MTRS・MTBSI | 合意した時間にサービスを利用できること ／ サービスが停止してから回復するまでの平均時間 ／ サービス停止の平均間隔 |
| RLO（目標復旧レベル） | 障害時に、どのレベルまでサービスを復旧させるか（RTO・RPOと合わせて決める） |
| ウォームスタンバイ | 待機系を起動途中の状態で待たせる。ホットとコールドの中間 |
| ITアセットマネジメント（ITAM）・ライセンスマネジメント | IT資産のライフサイクル全体の管理 ／ ソフトウェアのライセンスの保有数と使用数の管理 |
| 構成ベースライン・構成監査 | 特定の時点で承認された構成情報 ／ CMDBの内容が実際と一致しているかの確認 |
| 事業関係管理 | 顧客との良好な関係を維持するため、満足度の測定や苦情の対応を行う |
| 供給者管理 | 外部供給者・内部供給者の実績を管理し、契約やサービスレベルを守らせる |
| 需要管理 | サービスの需要を予測し、容量と合わせて調整する |
| 変更の種類 | **標準変更**（事前承認済みの定型的な変更）、**通常の変更**、**緊急変更**。実施後は **PIR**（変更実施後のレビュー）で評価する |
| サービス受入れ基準 | 新しいサービスや変更を本番に受け入れるための条件 |
| 重大なインシデント | 影響が非常に大きいインシデント。特別な手順で対応する |
| インシデントモデル | よくあるインシデントの対応手順をあらかじめ定めたもの |
| 解決目標時間 | インシデントの優先度ごとに定めた、解決までの目標時間 |
| プロセス成熟度・ギャップ分析 | プロセスがどの程度確立されているかの段階 ／ 現状とあるべき姿の差の分析 |
| AIOps | AIを使って、ログやメトリクスから障害の予兆検知や原因分析を自動化する運用 |
| 一次・二次・三次サポート | サービスデスクでの一次対応 ／ 専門部署 ／ 開発元・ベンダー |
| ジョブの管理 | ジョブスケジューリング、実行の監視、異常時の **復旧と再実行**（リラン） |
| 消火設備 | 泡消火、ハロゲン化物消火、**不活性ガス消火**（水を使わず機器を傷めない。サーバ室で使う） |
| コールドアイル・ホットアイル | サーバラックの吸気側の冷たい通路 ／ 排気側の暖かい通路。分離すると冷却効率が上がる |
| サージ防護デバイス（アレスタ） | 雷などの過電圧から機器を守る装置 |
| ティア（Tier）基準 | データセンタの設備の信頼性を4段階で評価する基準 |
| ZEB・LEED | 年間のエネルギー消費を実質ゼロにする建物 ／ 環境性能の高い建物の認証制度 |

## 16. システム監査

| 用語 | 意味 |
|---|---|
| 監査の種類 | **法定監査**（法律で義務付け：会計監査人監査など）と **任意監査**、**外部監査** と **内部監査**、**会計監査** と **業務監査** |
| 監査人の倫理 | 誠実性、客観性、専門的能力の保持と向上、正当な注意と秘密の保持 |
| 個別監査計画 | 個々の監査の対象、目的、手続、日程、担当者を定めた計画 |
| 統計的サンプリング | 母集団から統計的手法で標本を抽出し、全体を推定する監査技法 |
| 監査ソフトウェア・監査モジュール法 | 監査用のデータ抽出・分析ソフト ／ 本番プログラムに監査用のモジュールを組み込み、条件に合う取引を記録させる |
| 監査証跡 | 取引の発生から結果までを追跡できる記録（アクセスログ、トランザクションログなど） |
| JIS Q 19011 | マネジメントシステム監査のための指針 |
| クラウド情報セキュリティ管理基準 | クラウドサービスに特有の管理策を加えた、情報セキュリティ管理基準 |
| JIS Q 15001・プライバシーマーク | 個人情報保護マネジメントシステムの規格 ／ それに適合している事業者に付与されるマーク |
| 内部統制の限界 | 判断の誤り、共謀、経営者による無視などがあると、内部統制は機能しないことがある |
| COSOフレームワーク | 内部統制の国際的な枠組み（日本の基準の元）。**ERM** は全社的リスクマネジメント |
| 全社的な内部統制 | 組織全体に影響する統制（統制環境、方針など）。個々の業務プロセスの統制と区別する |
| CSA（統制自己評価） | 業務の担当者自身が、統制の有効性を評価する手法 |
| データガバナンス | 組織のデータを資産として管理するための方針・体制・ルール |
| CISO | 最高情報セキュリティ責任者 |
