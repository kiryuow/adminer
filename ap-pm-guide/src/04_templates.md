## 問1 情報セキュリティ

### ファイアウォールのルール表の読み方

| 項番 | 送信元 | 宛先 | サービス | 動作 |
|---|---|---|---|---|
| 1 | インターネット | DMZのWebサーバ | HTTPS | 許可 |
| 2 | 社内LAN | インターネット | HTTPS | 許可 |
| 3 | DMZ | 社内LAN | 全て | 拒否 |
| 4 | 全て | 全て | 全て | 拒否 |

- ルールは **上から順に評価** し、最初に一致したルールで動作が決まる（最後は「全て拒否」）。
- 「追加すべきルール」は、**必要な通信だけ**（送信元・宛先・ポートを最小限）を許可する。
- 応答の通信は、ステートフルな装置では自動で許可されることが多い（問題文の前提を確認）。

### 攻撃と対策の対応（頻出12）

| 攻撃 | 技術的対策 | 運用的対策 |
|---|---|---|
| フィッシング・標的型メール | 送信ドメイン認証、添付ファイルのサンドボックス検査 | 不審メールの訓練・報告ルール |

| SQLインジェクション・XSS | プレースホルダ、エスケープ、WAF | セキュアコーディング規約、脆弱性診断 |

| サプライチェーン攻撃 | 取引先との接続の制限、SBOM | 委託先の評価・契約での要求 |

## 問2 経営戦略

- **分析の型**：SWOT（内部／外部×プラス／マイナス）→ クロスSWOT（強み×機会＝積極戦略、弱み×脅威＝防衛・撤退）
- **計算の型**：限界利益率＝1−変動費率、損益分岐点＝固定費÷限界利益率、目標利益売上高＝（固定費＋目標利益）÷限界利益率
- **施策の狙いの型**：「（本文の課題）を解決するため、（施策）により（成果指標）を高める」

## 問3 プログラミング

### トレース表の作り方

| 回 | 変数1 | 変数2 | 条件の真偽 | 出力・戻り値 |
|---|---|---|---|---|
| 1 | | | | |

- ループ1回につき1行。**条件の判定結果** も列に書く。
- 再帰は「呼出しの木」を書く：呼び出すたびに右下に枝を伸ばし、戻ったら上の行に戻る。
- 空欄補充は、**ループの最初と最後の1回** だけを手でたどれば、境界の誤り（＜と≦、+1と−1）に気付ける。

## 問4 システムアーキテクチャ

| 求めるもの | 式 |

## 問5 ネットワーク

### パケットの流れの追い方

1. 送信元と宛先が **同じサブネットか** を確認（違えばデフォルトゲートウェイへ）。
2. 経路上の機器で、**アドレスが変わるか**（NAT・プロキシ・ロードバランサ）を確認。
3. 名前で通信する場合は、**DNSの問合せが先** に起きる。
4. VPN（IPsec）の区間は、**外側のヘッダ** がルータのグローバルアドレスになる。

## 問6 データベース

```
-- 集計の型
SELECT キー, COUNT(*), SUM(列) FROM 表 WHERE 行の条件 GROUP BY キー HAVING 集計の条件

-- 存在しないものを探す型
SELECT ... FROM A WHERE NOT EXISTS (SELECT * FROM B WHERE B.キー = A.キー)

-- 0件も含めて数える型
SELECT A.キー, COUNT(B.キー) FROM A LEFT OUTER JOIN B ON A.キー = B.キー GROUP BY A.キー

-- 順位の型（ウィンドウ関数）
SELECT 列, RANK() OVER (PARTITION BY グループ ORDER BY 値 DESC) FROM 表
```

- E-R図の多重度は、本文の「1つの〜に対して複数の〜」を **両方向から** 確認する。

## 問7 組込みシステム開発

- **状態遷移表**：「現在の状態」×「イベント」のマスごとに、本文の仕様の文を1つ対応させる。
- **時間計算**：周期＝1÷周波数、カウント値＝時間×クロック周波数。
- **電力計算**：平均電流＝Σ（電流×時間）÷全体の時間、駆動時間＝容量÷平均電流（時間→日の換算）。
- **タスク設計**：共有資源はセマフォで排他制御、優先度の高いタスクが低いタスクを妨げないか確認。

## 問8 情報システム開発

- **クラス図**：多重度（1、0..1、*、1..*）を本文の業務ルールで確認。継承（白抜き三角）と集約（ひし形）を区別。
- **テスト**：同値分割＋限界値分析（境界の両側）、分岐網羅の真偽。上位の代役＝ドライバ、下位の代役＝スタブ。
- **設計の意図**：「変更の影響を局所化するため」「共通処理を部品化するため」「障害時も処理を継続するため」

## 問9 プロジェクトマネジメント

| 本文の状況 | PMのとるべき行動の型 |
|---|---|
| 要件が固まらない | 要件の受付期限と変更手続を利用部門と合意する |
| 要員が業務に不慣れ | 業務に詳しい担当者を窓口に置く、事前に勉強会を開く |
| 予算・期限の変更が必要 | 承認権限を持つ組織（ステアリングコミッティ）に報告し承認を得る |
| リスクが特定された | 発生確率と影響を評価し、対応策と発動条件（トリガー）を決める |
| ステークホルダーの意見が対立 | 関係者を集めて合意形成の場を設け、決定事項を文書化する |

## 問10 サービスマネジメント

| 本文の活動 | どのプロセスか |
|---|---|
| 再起動して回復させた | インシデント管理（回避策） |
| 同じ障害の原因を調べる | 問題管理 |
| 設定を変える前に影響を評価して承認 | 変更管理 |
| 本番環境に展開・切り戻し計画 | リリース管理及び展開管理 |
| 将来の負荷を予測して増強 | 容量・能力管理 |
| 顧客と目標値を合意 | サービスレベル管理（SLA） |

- **要員数**：件数×1件の時間÷1人の対応可能時間 → 切り上げ。
- **停止時間**：サービス提供時間（24時間とは限らない）×（1−稼働率）。

## 問11 システム監査

### 監査手続の作文テンプレート

**「（監査証拠：記録・文書）を（技法：閲覧・突合・観察・インタビュー）し、（監査要点：コントロール）が（実施されている／機能している）かを確かめる」**

| 監査要点 | 監査証拠 | 技法 |
|---|---|---|
| 承認が行われているか | 承認記録、承認ログ | 閲覧・サンプリング |
| 職務分掌ができているか | 権限一覧、利用者ID一覧 | 閲覧・突合（人事記録と） |
| 定期的に見直しているか | 見直しの実施記録 | 閲覧 |
| 手順どおり作業しているか | 作業記録、チェックリスト | 閲覧・観察 |
| 説明が事実か | （説明を裏付ける）記録 | 閲覧・再実施 |
